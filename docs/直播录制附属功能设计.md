# 直播录制附属功能设计

## 目标

直播截获的主功能是实时监听和实时空间渲染。

长时间录制是可选附属功能，不默认开启，不应影响主监听链的稳定性和低延时。

## 三种运行模式

### 模式 A：仅实时监听

```text
Process Loopback
→ 有界环形缓冲
→ asmr3d 空间渲染
→ 耳机
```

特点：

- 不写磁盘；
- 不保存直播内容；
- 内存占用固定；
- 原始 PCM 被消费后立即覆盖；
- 最适合日常使用。

### 模式 B：滚动缓存

```text
Process Loopback
→ 有界滚动缓冲
→ asmr3d 空间渲染
→ 耳机
→ 可选“保存最近 N 分钟”
```

特点：

- 平时不保留最终文件；
- 保留最近 30 秒、1 分钟、5 分钟或可配置时长；
- 用户点击“保存最近片段”后，才把缓冲内容写入文件；
- 内存或临时磁盘占用有上限；
- 适合事故记录和回听最近内容。

### 模式 C：分段录制

```text
Process Loopback
→ 实时空间渲染
→ 编码器
→ 分段写入磁盘
→ 完成后释放原始 PCM
```

特点：

- 原始捕获 PCM 不保存；
- 只保存已经空间渲染的成品；
- 分段文件持续写入磁盘；
- 磁盘占用按录制时长线性增长；
- 可以配置最大空间、自动删除旧分段或达到上限后停止。

### 模式 C+：分段持续录制并自动合并

用户要求的新模式：

```text
直播开始
→ 实时空间渲染
→ 按固定时长连续分段写入
→ 不停止渲染、不丢失采样边界
→ 直播结束
→ 停止捕获
→ 校验全部分段
→ 合并为整段音频
→ 删除临时分段
```

该模式与普通分段录制不同：

- 分段只是临时写入单位；
- 用户最终得到单个完整音频；
- 各分段必须连续、无重叠、无采样缺口；
- 合并完成后才删除源分段；
- 合并失败时保留全部分段，允许重试。

## 直播结束判定

不能只依赖网页平台接口，因为平台不同。

采用分级判定：

1. 用户主动点击“停止直播截获”。
2. 目标进程退出。
3. 目标进程仍存在，但音频会话连续静音超过指定时间。
4. 音频会话消失，并且目标应用不再存在。

“静音”不能立即停止，因为直播可能短暂停顿。

建议默认：

```text
静音保护时间：15～30 秒
进程退出：进入 5 秒确认
用户手动停止：立即停止并合并
```

自动停止前应显示倒计时，并允许用户取消。

## 分段写入原则

每个分段必须：

- 使用相同采样率；
- 使用相同声道数；
- 使用相同位深；
- 以采样点边界切开；
- 具有连续序号；
- 记录起始样本位置和时长；
- 在直播结束后完成头信息。

推荐文件名：

```text
recording_20261004_130000.part001.wav
recording_20261004_130000.part002.wav
recording_20261004_130000.part003.wav
```

元数据文件：

```text
recording_20261004_130000.segments.json
```

内容示例：

```json
{
  "sample_rate": 48000,
  "channels": 2,
  "bit_depth": 24,
  "segment_seconds": 600,
  "segments": [
    {
      "index": 1,
      "file": "recording_20261004_130000.part001.wav",
      "start_sample": 0,
      "frames": 28800000
    }
  ]
}
```

## 合并方式

### WAV 16-bit / 24-bit

如果最终文件小于约 4 GB：

```text
读取每个分段头
→ 校验格式和样本位置
→ 顺序复制 PCM 数据
→ 写入新的 RIFF/WAV 头
→ 写入 SHA-256
→ 删除临时分段
```

合并过程中不需要重新编码，CPU 开销很低。

### 超过 4 GB

普通 WAV 的数据长度字段最多表示约 4 GB。

长时间录制应使用：

```text
RF64
```

或自动切换为：

```text
分段 WAV + M3U/CUE 播放列表
FLAC
Matroska
```

推荐直接输出 RF64，实现真正连续的单个音频文件。

### FLAC

不能把多个独立 FLAC 流直接二进制拼接后当作一个合法 FLAC。

可选：

1. 分段保存 FLAC，结束时解码后重新编码成单个 FLAC；
2. 保留分段 FLAC，并生成 M3U/CUE；
3. 内部先写 WAV/RF64，结束后编码成 FLAC。

无损合并重新编码会带来额外 CPU 和磁盘读写。

## 合并后的删除策略

正确处理顺序：

```text
生成最终整段文件
→ 校验长度、样本总数和 SHA-256
→ 完整读取验证
→ 删除临时分段
→ 清理元数据
```

不能在合并完成前删除分段。

峰值磁盘占用约为：

```text
临时分段 + 最终整段文件 ≈ 2 倍成品大小
```

因此 5 GB 成品至少应预留 10 GB 以上空间。

如果磁盘空间不足，可以：

- 保持分段模式，不合并；
- 生成无缝播放列表；
- 将最终文件写入另一个磁盘；
- 只保留指定时间段。

## “实时删除”的正确含义

可以实时释放：

- 已消费的原始捕获缓冲；
- 已编码完成的数据块；
- 已写入磁盘的临时 PCM 块；
- 滚动模式中过期的最旧片段。

不能自动删除：

- 用户要求保留的完整成品；
- 尚未结束的最终文件；
- 分段模式下仍需保留的历史分段。

因此建议把功能表述为：

```text
边处理边释放，原始音频不长期驻留
```

而不是：

```text
生成完整录音后自动删除
```

## 推荐实现

### 环形缓冲

原始捕获进入固定大小的环形缓冲：

```text
容量：1～5 秒
消费后覆盖
不写磁盘
```

这可以隔离实时线程和磁盘写入速度，避免无限增长。

### 渲染输出分流

```text
空间渲染输出
├── 实时耳机监听
└── 可选录制编码器
```

监听和录制应使用独立分支，录制堵塞时不能阻塞耳机输出。

### 分段写入

建议默认按时间切段：

```text
5 分钟
10 分钟
30 分钟
```

原因：

- 避免单文件过大；
- 降低意外中断损失；
- 便于自动删除旧文件；
- 避开普通 WAV 的 4 GB 文件长度限制。

### 格式建议

| 格式 | 每小时大小，约 | 特点 |
|---|---:|---|
| WAV 16-bit | 691 MB | 无损、CPU 低、文件大 |
| WAV 24-bit | 1.04 GB | 无损、文件更大 |
| FLAC | 350～650 MB | 无损压缩、CPU 中等 |
| Opus 192 kbps | 86 MB | 有损、体积小、适合长录 |

长时间录制优先考虑：

```text
FLAC 分段
```

如果只做长时间留档且接受有损压缩，可以使用 Opus。

## 磁盘空间管理

建议提供一个总空间上限：

```text
2 GB / 5 GB / 10 GB / 自定义
```

达到上限时可选：

- 删除最旧分段；
- 停止录制但保持监听；
- 自动转换为更低码率格式；
- 弹出用户提示。

录制前应检查：

- 可用磁盘空间；
- 目标目录是否可写；
- 是否位于可移动设备；
- 是否可能进入睡眠；
- 是否存在云同步或杀毒软件频繁扫描。

## UI 建议

直播截获区增加附属录制设置，但默认关闭：

```text
录制模式：
关闭 / 保存最近 N 分钟 / 连续分段录制

格式：
WAV 16-bit / WAV 24-bit / FLAC / Opus

分段：
5 / 10 / 30 分钟

空间上限：
2 / 5 / 10 GB

达到上限：
删除最旧 / 停止录制
```

主界面始终保留：

```text
开始监听
停止监听
输入电平
监听设备
```

录制状态应显示：

- 已录制时长；
- 当前文件大小；
- 预计剩余空间；
- 已写分段数量；
- 写入错误；
- 磁盘速度异常。

## CPU 与磁盘估计

实时监听本身不需要持续写磁盘。

启用录制后增加：

```text
PCM 编码和文件写入：1%～8% 单核
磁盘写入速度：
WAV 16-bit：约 192 KB/s
WAV 24-bit：约 288 KB/s
```

磁盘写入速度不高，主要风险是：

- 长时间运行稳定性；
- 系统睡眠；
- 磁盘被拔除；
- 云同步和杀毒扫描；
- 空间耗尽；
- 普通 WAV 的 4 GB 上限。

## 最终定位

```text
主功能：直播实时截获和空间渲染
附属功能：可选的连续分段录制，直播结束后自动合并
默认状态：录制关闭
原始捕获：只保留短暂的环形缓冲
成品保存：由用户主动启用
```
