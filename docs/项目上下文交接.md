## 3. 关键决策与原因

### 3.1 直播截获为什么必须用进程回环 + .NET Core

实测结论（不要重复试错）：

| 宿主 | 进程回环 |
|---|---|
| PowerShell 7（.NET 9） | ✅ 可用 |
| Windows PowerShell 5.1（.NET Framework 4.x） | ❌ 固定返回 `E_ILLEGAL_METHOD_CALL (0x8000000E)` |

已排除的因素：COM 单元（STA/MTA/独立 MTA 线程）、回调对象形式（托管接口 /
顶层 ComVisible / 手写非托管 vtable）、P/Invoke 形式（接口参数 / 原始指针 /
GetProcAddress + 委托）、进程位数、应用清单。**结论就是 CLR 差异，没有绕过办法。**

代价：必须随包带一个 .NET Core 宿主 → 选了 PowerShell 7 自包含版（内置）。

### 3.2 为什么删掉"系统输出回环"

设备回环抓的是端点混音，**asmr3d 自己的输出也在里面** → 输出被再次采集 →
自激回路 → 多层回声/啸叫。已从捕获端、脚本、界面、文档全部移除；
没有 PowerShell 7 时只提示，不再回退到会啸叫的模式。

### 3.3 回声是怎么消掉的（关键技巧）

实测的音频引擎行为：

| 操作 | 对进程回环捕获的影响 |
|---|---|
| 会话音量 = 0% | 捕获变成数字零，链路断掉 |
| 会话音量 = 10% / 1% / 0.1% | 捕获**精确**等比缩小（每十倍档恰好 −20 dB） |
| 设备级静音 | 捕获不受影响 |

所以"压低原声 + 渲染链补偿"是无损的：

```text
记下原音量 → 设为 0.1%（−60 dB）→ 渲染链乘 (原音量 / 0.001)，上限 +66 dB → 停止时恢复
```

粉噪声实测：`0.01` 衰减约 40.3 dB，`0.001` 衰减约 60.3 dB，且 `0.001`
下捕获仍有完整信号，不是数字零。

千万别改成"会话静音"——那会连捕获一起静掉。
音量恢复有三层兜底：停止时 / 退出时 / 崩溃后下次启动读
`%APPDATA%\asmr3d空间渲染器\source-volume-state.json`。

### 3.4 录制分流点的位置

```text
… → master → 限幅器 → 【录制分流】→ monitorGain → 输出设备
```

分流放在**监听之前、渲染链末端**，因此：

- 录制内容 = 送往耳机的信号（实时调参会被录进去，已验证方位角 −90°→+90°
  在成品里体现为 L-R 从 +12.79 dB 变到 −16.27 dB）；
- 即使勾选"静音本地监听"，录制依然拿到完整 3D 成品。

不要把它挪到 monitorGain 之后，否则静音监听模式会录出空文件。

### 3.5 视频转音频不依赖 ffmpeg

Electron 自带的解码器能直接解 MP4 音轨：

```text
decodeAudioData(MP4) → 26.39 s / 48000 Hz / 2 ch
```

所以用"解码 → 分块编码 WAV"实现，实测 355 MB / 63.7 分钟的 MP4 → 1.02 GB
24-bit WAV 用时 **14.5 秒**。硬性检查：时长 ≤ 6 小时、输出 < 3.8 GB（RIFF 限制）、
预计内存 < 可用内存 × 85%。不支持 MKV（Chromium 无法解该封装）。

### 3.6 近场距离保护

用户反馈距离低于约 0.40 m 时，稍微调整会明显变干、贴耳，形成"空耳感"。
原因不是单一距离增益，而是四个变化叠加：

```text
1/r 距离增益上升
+ 近场低频提升上升
+ HRTF 近距离外化变差
+ 混响湿声下降
```

现在采用以下保护：

- `spatialDistance = max(distance, 0.35 m)` 用于 HRTF 位置、空气吸收和混响外化；
- 距离响度仍使用真实 `distance`，所以 0.2 m 仍比 0.4 m 更响；
- 浏览器 HRTF 增加独立距离补偿，抵消空间距离保护带来的音量变化；
- 近场低频上限从 5 dB 收到 3 dB；
- 混响湿声最低保留 0.12，不再降到 0.04。

打包版 UI 验收：

```text
0.40 m → 距离增益 -6.0 dB · 近场 2.7 dB · 空气吸收 19.6 kHz
0.35 m → 距离增益 -4.9 dB · 近场 3.0 dB · 空气吸收 19.7 kHz
0.30 m → 距离增益 -3.5 dB · 近场 3.0 dB · 空气吸收 19.7 kHz
0.20 m → 距离增益  0.0 dB · 近场 3.0 dB · 空气吸收 19.7 kHz
```

## 4. 踩过的坑（避免重复）

| 现象 | 真正原因 | 处理 |
|---|---|---|
| `Add-Type` 报 "Could not find a part of the path ...\ref" | 精简内置 PowerShell 时删掉了 `ref\` | 保留 `ref\`，它是编译用的引用程序集 |
| 精简后 PowerShell 起不来（`LanguagePrimitives` 初始化失败） | 删得太狠（连 WPF/WinForms 一起删且缺少必需项） | 只删那 12 个 WPF/WinForms/UIAutomation 文件，实测安全 |
| 改了内置路径但没生效 | `resolvePowerShell()` 里 PATH 查找排在包内路径之前 | 包内路径优先级提到 PATH 之前 |
| 进度条只能点击、不能拖动 | `input` 事件里调用 `updateProgressUI()` 反复改写 `max`，Chromium 会中断拖拽 | `max`/`value` 仅在真正变化时赋值；拖拽中只更新文本 |
| 长音频导出报 `Unable to decode audio data` | Chromium 的 `decodeAudioData` 单次最多解出 **2 GiB PCM**（2^31 字节）；48 kHz 立体声约 **93 分钟**。实测 210 MB 切片（91 分 45 秒 / 1.969 GiB）可解，215 MB 起必失败 | 加前置时长检查 + 把解码异常换成中文提示；根本解法需分段解码（见下方"后续可做"） |
| 选完文件直接导出时读不到时长 | 音频元素还没挂上源文件（`ensureAudioGraph()` 要等播放才创建）。导出路径里补了 `src/load()` + 等 `loadedmetadata` | 已在 `startOfflineExport()` 中处理 |
| 点击停止后进度归零 | `stopButton` 里写了 `currentTime = 0` | 停止只暂停，保留位置 |
| 录制到盘符根目录 `D:\` 报 `EPERM mkdir` | Node 在盘符根目录上调 `mkdirSync` 即使已存在也会抛 | 目录存在就不再 mkdir，并加可写性探测 |
| 选文件后"转换为 WAV"按钮点不动 | 重构时漏了 `disabled = false` | 选择文件后显式启用 |
| 转换大文件时窗口假死 | 编码是同步循环 | 每 64K 帧 `await` 让出主线程并刷新进度 |
| EXE 图标看着没变 | Windows 外壳图标缓存 | 是缓存问题，文件内已是新图标（可字节级验证） |
| `-MuteState true` 传参失败 | `-File` 方式传参是字符串，`[bool]` 绑不上 | 改用 `[string]` 再自行解析 |
| PowerShell 脚本里的中文变乱码 | PS 5.1 按 ANSI 读无 BOM 的 .ps1 | 脚本里不放非 ASCII 字面量；并设置 `[Console]::OutputEncoding` |
| 内嵌 C# 在 PS 5.1 编译失败 | 用了 C# 7 语法（out 变量等）+ CodeDom 默认引用缺失 | 写 C# 5 兼容代码，直接 `Add-Type -TypeDefinition` |
| 整页截图里背景图错位 | `background-attachment: fixed` 与 `captureBeyondViewport` 冲突 | 属截图假象，视口截图正常 |

## 6. 已知限制与后续可做的事

### 超长文件的分段离线导出

浏览器一次最多解出约 2 GiB PCM（48 kHz 立体声约 93 分钟），超长文件原本无法
"完整文件（离线渲染）"导出。现在会自动改走分段路径：

```text
按字节把源文件切成若干段（默认每段约 30 分钟）
→ 逐段 decodeAudioData + OfflineAudioContext 渲染
→ 追加进 WavBlobBuilder（Blob 分片，磁盘承载）
→ 最后补 WAV 头输出一个完整文件
```

**只有 MP3 可以这样切**，实测结论（中段 20/60 MB 切片是否可解码）：

| 格式 | 中段切片 | 原因 |
|---|---|---|
| **MP3** | ✅ 可切 | 帧自包含，解码器会自己找同步字；切片起点用 `0xFFEx` 同步字对齐避免开头杂音 |
| FLAC | ❌ | 解码器需要文件开头的 STREAMINFO |
| OGG / Opus | ❌ | 需要开头的 codec setup 头 |
| MP4 / M4A | ❌ | 需要开头的 moov |

其它格式遇到超长文件时给出的是明确提示（改成 MP3、或切成几段），不会再抛
`Unable to decode audio data`。

实测（299 MB / 2 小时 11 分的 VBR MP3）：5 段各 30 分钟，总耗时 **114 秒**，
成品 1.44 GB / 16-bit，总长 7851.0 秒与源文件完全一致；各接缝前后 1 秒窗口的
电平一致（无静音、无缺口）。

注意：切片起点只能对齐到 MP3 帧，理论上每个接缝最多损失不到一帧（约 26 ms），
实测听不出。

**限制**

- 直播截获仅 Windows；只支持按应用捕获。
- 视频转换不支持 MKV、H.265/AC3 等 Chromium 解不了的编码。
- 长音频转换/导出受内存限制（解码缓冲常驻），有前置提示。
- 包体 233.8 MB，主要是 Chromium + 内置 PowerShell。

**可选优化（均已实测过可行性）**

| 优化 | 省多少（zip） | 风险 |
|---|---|---|
| `locales` 只留 `zh-CN` + `en-US` | ~12 MB | 低 |
| 构建时预编译 C# 捕获代码为 DLL，去掉 Roslyn + `ref\` | ~13 MB | 中 |
| 不内置 PowerShell，改回依赖系统安装 | ~83 MB | 用户需自行安装 |

**可能的下一步**

- 流式解复用（mp4box.js + WebCodecs）替代 `decodeAudioData`，彻底摆脱内存限制。
- ~~分段解码~~ **已实现（v0.2）**：见下方"超长文件的分段离线导出"。
- 原生 C++ 捕获助手替代 PowerShell（需要 C++ 工具链），可同时去掉 83 MB。
- Android APK 重新评估（当前暂停）。
