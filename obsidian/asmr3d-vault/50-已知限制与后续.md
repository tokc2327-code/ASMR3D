# 50 已知限制与后续

[[00-索引]] · 相关：[[30-关键决策与原因]] · [[32-实测数据与验证]]

## 当前硬限制

### 平台

| 能力 | 限制 |
|---|---|
| 直播截获 | 仅 Windows 桌面版 |
| 捕获范围 | 仅按应用进程回环 |
| 系统输出回环 | 已删除，不恢复 |
| Android APK | 暂停维护 |
| 手机 PWA | 可用，但无直播截获 |

### 格式与解码

| 限制 | 数值 / 原因 |
|---|---|
| `decodeAudioData` 单次 PCM | 约 2 GiB |
| 48 kHz 立体声时长 | 约 93 分钟 |
| 44.1 kHz 立体声时长 | 约 101 分钟 |
| 可自动中段分段 | 仅 MP3 系 |
| FLAC 中段切片 | 缺少 STREAMINFO，不可 |
| OGG / Opus 中段切片 | 缺少 codec setup，不可 |
| MP4 / M4A 中段切片 | 缺少 moov，不可 |
| MKV | Chromium 不支持封装 |
| H.265 / AC3 / DTS | 内置解码器通常不支持 |
| WAV 单文件 | RIFF 约 4 GB，程序保守用 3.8 GB |

### 音频模型

- 双耳兼容是整体声场处理，不恢复对象；
- 普通双耳录音不能可靠反解独立三维声源；
- 通用 HRTF 有个体差异；
- 距离是主观模型；
- 参数化 HRTF 不是实测 HRIR 数据库；
- 不对绝对定位和头部追踪作承诺。

### 资源

- 包体约 234 MB 压缩、562 MB 解压；
- 内置 PowerShell 约占 83 MB 压缩；
- 长音频解码缓冲常驻内存；
- 直播合并峰值磁盘约占成品 2 倍；
- 大文件转换或导出仍受可用内存影响。

## 已实测可行的体积优化

| 优化 | 预计节省 zip | 风险 | 说明 |
|---|---:|---|---|
| `locales` 只留 `zh-CN` 和 `en-US` | 约 12 MB | 低 | 失去其它语言 |
| 预编译 C# 捕获代码，去掉 Roslyn 和 `ref\` | 约 13 MB | 中 | 需要新的构建步骤 |
| 不内置 PowerShell，依赖用户安装 | 约 83 MB | 高 | 破坏开箱即用 |

选择优化前要重新测捕获、`Add-Type`、启动和 Windows 版本兼容。

## 可能的工程改进

### 流式解复用

目标：摆脱 `decodeAudioData` 的 2 GiB 限制。

可行方向：

```text
mp4box.js
  → WebCodecs AudioDecoder
  → 分块 PCM
  → WavBlobBuilder
```

收益：

- 支持更长 MP4 / M4A；
- 内存占用可随流控制；
- 可以统一视频转音频与超长导出。

代价：

- 增加依赖和封装复杂度；
- 需要处理不同编码、容器和采样格式；
- WebCodecs 支持矩阵需要实测。

### 原生 C++ 捕获助手

目标：去掉 PowerShell 和 Roslyn。

收益：

- 包体可减少约 80 MB；
- 启动更快；
- 进程控制更直接。

代价：

- 需要 C++ 工具链；
- 需要维护 MSVC 构建；
- 签名和杀软误报风险更高。

更保守的方案是把 C# 捕获代码预编译为 DLL，只去掉 Roslyn / `ref\`。

### 本地化裁剪

只保留 `zh-CN` 和 `en-US` 最容易落地，但会失去未使用的语言包。

### 录制恢复

当前合并失败会保留分段和元数据。可以增加：

- 启动时扫描未完成录制；
- 提供“从分段恢复”按钮；
- 计算已完成总长度；
- 断点续合。

这是比重新捕获更实际的稳定性改进。

### 模板扩展

可以增加：

- 批量为多个文件套用同一模板；
- 模板队列；
- 只覆盖指定字段；
- 模板版本迁移；
- 在导出元数据中记录模板哈希。

### 播放和导出的内存提示

当前已经有前置估算，可以进一步：

- 在选文件时显示一次内存曲线；
- 显示预计峰值磁盘；
- 给“先转 MP3 再分段”的操作提示；
- 对 16-bit / 24-bit 做体积对比。

## Android 重新评估的条件

重新开启 APK 前需要先确认：

- 第三方工具链和许可证风险可控；
- 目标 Android 版本允许 AudioPlaybackCapture；
- 目标应用是否允许被捕获；
- 是否值得维护原生构建；
- PWA 是否已经满足主要移动场景。

即使重新开启，Android 直播捕获也不能承诺覆盖所有应用。

## 不应做的“优化”

| 做法 | 问题 |
|---|---|
| 用系统输出回环减少捕获代码 | 会重新引入自激啸叫 |
| 用会话静音消除回声 | 捕获变数字零 |
| 把 monitorGain 移到录制分流前 | 静音监听录出空文件 |
| 把所有文件都按字节切 | FLAC / OGG / MP4 中段不可解 |
| 去掉 `ref\` 省体积 | `Add-Type` 失败 |
| 直接承诺 MKV / H.265 支持 | Chromium 解码器不覆盖 |
| 声称可定位双耳录音中的独立对象 | 技术上不可靠 |

## 模型接手时的优先级

如果只是继续维护：

```text
1. 保持捕获和录制稳定
2. 保持超长文件路径有明确提示
3. 保持输出目录和状态恢复
4. 不让包体继续无意义增长
5. 更新 Wiki / Obsidian 与版本同步
```

如果要开发新版本：

```text
1. 先写可复现实验
2. 再改实现
3. 更新 docs / wiki / obsidian
4. 用 Dev 和打包版各测一次
5. 最后再发版
```

## 仍需重新验证的事项

- 不同 Windows 音频驱动上的进程回环稳定性；
- 44.1 kHz 设备下的长时间漂移；
- 多显示器 / 不同 DPI 的界面布局；
- 超长 FLAC / OGG 的用户替代流程是否足够清晰；
- 合并 4 GB 以上录制的 RF64 兼容性；
- 长时间直播录制的磁盘空间预估。

这些不是已知失败项，而是下一次版本发布前值得补测的边界。
